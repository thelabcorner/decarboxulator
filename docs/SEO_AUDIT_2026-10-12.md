# Decarboxulator V4 — SEO and migration audit
**Date:** 2026-10-12  
**Release target:** GitHub Pages, `https://thelabcorner.github.io/decarboxulator/`  
**Future target:** `https://dcxr.thedabcorner.site/` — **not yet DNS active**.

## Non-negotiable: preserve V3 indexed URLs

V3's published routes were inspected from the archival `decarboxulator` checkout. The V4 migration registry maps the 15 historically relevant HTML pages to conceptually equivalent V4 content, including `index-old.html`; 13 extensionless calculator aliases are also generated. Two time-predictor endpoints display a truthful retired-feature explanation rather than masquerading as a working replacement. Legacy `#backward` links still open the reverse THC → THCa calculation.

The SEO validator now pins **all 15 legacy mappings independently of the editable redirect manifest**, so accidentally removing or repointing an old indexed URL fails the build. Active migration pages combine a zero-second meta-refresh with a destination canonical and JavaScript history replacement for browsers. They do **not** combine `noindex` with these redirect signals. The time-predictor notices remain `noindex,follow`.

GitHub Pages project sites do not provide native configurable 301 status redirects. Google's documented instant meta-refresh support is the best available HTML-only permanent-move signal. An actual HTTP 301 would be preferred if platform/hosting changes in the future.

## Discoverability and verified facts

- Exactly **11 static, unique canonical pages**: landing, eight tools, FAQ, and reference. Each has its own server-rendered H1/title/description/OG PNG; sitemap entries are checked against actual HTML canonical values.
- The historical V3 sitemap location `/resources/assets/sitemap.xml` now publishes the **same current canonical URL inventory** as `/sitemap.xml`. The old submitted URL is not abandoned.
- The original V3 Google Search Console HTML verification token is present on prerendered V4 pages; GA4's original measurement ID remains unchanged by this campaign.
- A new built-HTML crawl covers anchor destinations and prevents accidental links outside the GitHub Pages `/decarboxulator/` mount. Baseline: **202 internal links, 67 external links across 11 pages**; no missing internal targets.
- The existing 85 FAQ question/answer instances across 10 pages are checked against the actual rendered markup, not just JSON-LD.
- Historical Github Pages root and the planned custom-domain root are built independently; both go through SEO checks. Do **not** switch canonicals to `dcxr` while its DNS remains unresolved.

**Important qualification:** `/decarboxulator/robots.txt` on GitHub Pages is *not* the origin-level `/robots.txt` used for robot-exclusion directives. The sitemap is valid at the project path, but submit `https://thelabcorner.github.io/decarboxulator/sitemap.xml` directly in Search Console. Do not report a nested robots.txt as origin-wide crawler control.

## Recommended Search Console follow-through

1. Keep the **existing** GitHub Pages property verified. Submit both current and historical sitemap URLs (which now advertise identical canonical destinations). Check the indexed coverage report and URL Inspection for representative historical links.
2. Monitor **search clicks, impressions, queries, indexed status, canonical selected by Google, 404s and redirect validation**, broken down by V3 URL versus V4 URL. Look at at least a 28-day window; avoid claiming improvement from build-time metrics.
3. Once Cloudflare DNS and the GitHub Pages custom-domain switch both work, verify `dcxr.thedabcorner.site` in Search Console, submit its root sitemap, and use the documented cutover checklist in `docs/DEPLOYMENT.md`. Test that old GitHub links map to the *corresponding* new tool, not the homepage.
4. Use actual Search Console performance data before retitling the existing high-traffic THCa/THC pages. The landing and forward tool share some search intent; aggressive keyword changes could hurt old rankings.
5. Run Chrome real-user Core Web Vitals (LCP, INP, CLS) and compare mobile versus desktop. The client build includes a substantial JS entry chunk; SSR makes core content crawlable but does **not** establish strong interaction or paint performance. Optimize measured bottlenecks without inventing a speed/SEO lift.
6. Keep the scientific reference's primary literature links and visible methodology content current. Preserve realistic limitations. Don't represent ideal stoichiometric results as guaranteed process yields.

## Structured-data expectations

The site uses `WebApplication`, `WebPage`, `WebSite`, `BreadcrumbList`, `TechArticle`, `Person`, `Organization` and `FAQPage` where appropriate. Google limits FAQ *rich result display* to well-known authoritative government/health sites; valid `FAQPage` markup alone does not confer a rich-result benefit. Avoid introducing fictional ratings, awards, or reviews to chase appearance enhancements.
